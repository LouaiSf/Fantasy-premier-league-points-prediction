## Outcome and constraints

The Chip Advisor must open without a runtime error and must never display recommendations from an incompatible response. My Team must describe an owned squad's finances correctly after price moves. The transfer recommendation must be readable as OUT, IN, and the resulting photographed XI, with no collision with the matchday rail. Apply the same finance basis to Transfer Studio and chip simulations. Keep the existing Flask, Next.js, PuLP, local-storage, and broadcast design architecture.

Preserve the user's modified `all_seasons_data_final.csv`, `data/2026-27/{fixtures.csv,players_raw.csv,gws/merged_gw.csv}`, and untracked continuation/generated files. Stage only files owned by each phase. Do not add co-author trailers. Commit and push each completed, verified phase to `origin/main` when safe; never force-push.

`DESIGN.md` currently limits its scope to the prototype. Before touching production UI, extend its scope and Component section to cover the Next.js My Team and Chip Advisor components below, using the existing CSS tokens in `webapp/frontend/app/broadcast.css`. Do not replace the established PL purple, pink OUT, lime IN, cyan focus, typography, or `PlayerPhoto` fallback.

## Phase 1: one finance model for owned squads

**Files:** `webapp/frontend/lib/types.ts`, `lib/squad.ts` (or a focused `lib/finance.ts`), `components/providers/app-provider.tsx`, `components/team/squad-editor.tsx`, `components/team/manager-lineup-preview.tsx`, `app/team/page.tsx`, `app/transfers/page.tsx`, `webapp/platform_data.py` / `webapp/app.py` for price timestamp.

1. Introduce a versioned `StoredSquad` finance block independent of the lineup's `source`: `bankTenths`, `ownedPrices` keyed by element ID with `purchaseTenths` and optional imported `sellingTenths`, `priceBasis` (`imported`, `manual`, `estimated`), `marketPriceAsOf`, and `lineupGameweek`. Keep season, IDs, XI/bench IDs, armbands, and source metadata. Validate all 15 unique IDs and the finance fields when reading localStorage. Migrate the current storage shape without deleting a squad. For unknown legacy purchase prices use `priceBasis=estimated`, preserve any stored bank, and state that transfer affordability is an estimate.
2. Use integer tenths for price arithmetic. For an owned player with purchase `P` and current market `C`: if `C <= P`, selling price is `C`; otherwise selling price is `P + floor((C-P)/2)`. At import, retain the upstream `purchase_price` and `selling_price` for each pick, compare the latter with the formula as a consistency check, and label the GW/time at which it was observed. Example: 5.0→5.3 sells for 5.1; 5.0→4.7 sells for 4.7. The current market can later change; recompute using retained purchase price and refreshed market data. Do not silently replace purchase with current value on page reload.
3. Treat imported public picks as a snapshot. `fpl_client.py` reads picks and bank from `entry_history` for the resolved lineup GW; this may be behind transfers made since then. Show `As of GWn` beside bank/selling data and offer re-import or an explicit editable bank when the user needs the current squad. If local `players_raw.csv` changes, expose its mtime as `market_prices_updated_at` in `/api/platform`; show that timestamp and a stale-price warning after 24 hours. Also expose `predictions_older_than_market` when the prediction export predates the market file; keep point projections labeled by their own timestamp. Do not describe an old snapshot as live account synchronization.
4. New manual squad: at first save, require the selected 15 to fit £100.0m **at that save time**, store each selected market price as purchase price and the leftover bank. Later rises do not invalidate the owned squad. Existing legacy/manual squads with no purchase history must not be declared illegal from current market sum; offer import/finance correction and mark affordability estimated. In the squad editor, retain current shape and three-per-club validation and add a clear spend/remaining readout and a specific initial-budget error. Distinguish this new-squad flow from editing an existing owned squad, where bank + proceeds of removed players determines affordability.
5. On restore, only warn if IDs are missing, duplicate, wrong-season, finance data invalid, or a **proposed transfer** is unaffordable. Replace `Squad over budget (£X.Xm)` with `Current market value £X.Xm` and `Estimated/known selling value £Y.Ym`; show bank separately. Remove `100 - current spend` and the red `is-over` presentation for an appreciated owned squad. Preserve the finance block when only XI/bench/captain changes; on an applied transfer remove outgoing ownership rows, add incoming at current purchase price, and save the solver's `bank_after`.
6. Give the shared provider one finance state used by My Team and Transfer Studio. Do not keep separate default-zero bank sources. Persist edits to bank in tenths, and invalidate any analysis that used the old bank/squad/market snapshot.

**Acceptance cases:** (a) 15 purchased for £99.5m, bank £0.5m, current market total £101.2m: no over-budget toast or negative bank; (b) player bought £5.0m, market £5.3m: UI/solver sale £5.1m; (c) player falls to £4.7m: sale £4.7m; (d) reload and lineup optimization preserve ownership prices and bank; (e) a genuinely unaffordable proposed move is blocked with the missing amount.

## Phase 2: make the optimizer spend sale proceeds

**Files:** `scripts/optimise.py`, `webapp/app.py`, `webapp/frontend/lib/api.ts`, `lib/types.ts`, `tests/test_optimise.py`, `tests/test_webapp.py`.

1. Extend `POST /api/transfers` with `selling_prices_tenths: { [elementId]: number }` for all 15 owned IDs and use the existing `bank` field, or replace it with `bank_tenths` in one atomic API migration. Validate finite nonnegative numbers, unique element IDs, exact ownership keys, and season identity; return a 400 with a named field if invalid. Keep the old request contract only if an existing shipped caller requires it; otherwise update both Next callers together.
2. Before solving, join `data/<season>/players_raw.csv` `id,now_cost` onto both `s['players']` and `s['everyone']` by `element`, and use `now_cost/10` as the **single current purchase-price source** for `/api/platform`, `/api/transfers`, and chip optimization. Keep `predicted_points` from the model file. Fail or mark a player non-purchasable if the current market row is missing; never silently fall back to an old prediction-export price. Cache/reload this joined market view when either file's mtime changes, not only when the prediction file changes. A focused contract check should confirm matching `element` prices in platform and transfer responses despite an older prediction export.
3. In `compute_transfers`, define available spending as `bank + Σ selling_price(owned)` and an **effective solver cost** per candidate: selling price for a retained owned player, current purchase price for a newly acquired player. Add a cost-column argument to `solve_squad` (or equivalent) so this accounting does not overwrite `value_m` used for display and player records. The constraint `Σ effective_cost(selected) <= bank + Σ selling_price(owned)` exactly enforces `bank + sales_out - purchases_in >= 0` while preserving squad size, position, club, and transfer-count constraints. For unavailable owned players, keep their selling proceeds in the budget and mark them forced out as the existing code does.
4. Compute `bank_after` from effective cost in tenths, and keep separate `market_value`/`selling_value` fields in the response. `spend` must be clearly documented as market value if it remains inherited from `lineup_payload`; do not show it as transfer cash spent. Update `/api/lineup` only as needed so reordering a squad never resets the finance ledger.
5. Apply the same finance budget to Free Hit/Wildcard candidate squads in `compute_chips` when a tailored 15 and finance data are available. Pass bank/ownership prices through `/api/chips`. If the basis is missing or stale, present fixture signals or a provisional verdict and explain the limitation; do not display a precise player-level chip gain calculated with a fictional market-value budget.
6. Add compact optimizer tests for one rising and one falling owned player, the required two-transfer downgrade/upgrade combination, zero-transfer hold, and `bank_after >= 0`. Check the API rejects incomplete price maps. These protect a subtle monetary boundary; no broad repetitive test suite is needed.
